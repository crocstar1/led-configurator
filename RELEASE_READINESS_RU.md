# Готовность прошивки к выпуску

Дата актуализации: 28 июля 2026 года.

Этот документ сводит в один план:

- технический аудит готовности Test-led;
- функциональное сравнение с исходной прошивкой `proj1`;
- архитектурную ретроспективу;
- фактическое состояние текущих исходников и незакоммиченного рабочего дерева.

Источником фактического поведения считается текущий код. `PROJECT_STATE.md`,
README и учебные документы используются как справочные материалы и могут
отставать от реализации.

## 1. Однозначный статус

| Уровень | Текущий статус | Краткий вывод |
|---|---|---|
| Сборка и прошивка | **Готово** | Пользователь подтвердил успешную сборку текущего LED reliability pass. Стендовую ESP32 можно прошивать. |
| Стендовые аппаратные испытания | **Можно начинать** | Архитектура и защитные механизмы достаточны для контролируемого стенда, но электрические входы, реальная матрица и отказные режимы ещё не приняты. |
| Контролируемый пилот | **Пока не готово** | Нужны успешная аппаратная приёмка, фиксация текущего reliability pass, системная диагностика, закрытие конкурентного доступа к LED state и процедура ввода в эксплуатацию. |
| Production без постоянного наблюдения | **Не готово** | Не завершены длительный прогон, контроль версии/принадлежности OTA, диагностика отказов и подтверждение восстановления после питания, сети и повреждённых настроек. |

Выбранный путь: **вариант B — умеренная production-доводка небольшими
независимыми commits без большого переписывания архитектуры**.

ArduinoJson, LittleFS, runtime-размер матрицы, универсальная EVSE-архитектура и
перенос старого frontend не входят в выбранный план.

## 2. Состояние рабочего дерева

На момент аудита:

- ветка: `main`;
- последний зафиксированный commit: `0821c35`;
- `origin/main` указывает на тот же commit;
- LED reliability pass находится в рабочем дереве и успешно собран
  пользователем, но ещё не зафиксирован отдельным commit;
- изменены `src/led_manager.cpp`, `src/led_manager.h`, `src/main.cpp` и
  `src/gui_html.h`;
- в `src/status_mapper.h` есть отдельное форматирование и поясняющий комментарий,
  не относящиеся к LED reliability pass.

Перед дальнейшими функциональными изменениями reliability pass следует
зафиксировать отдельно. Изменение `status_mapper.h` нельзя незаметно включать в
этот commit: его нужно либо оставить для отдельного документационного/стилевого
этапа, либо осознанно отклонить.

## 3. Текущая архитектура

Главный рабочий путь:

```text
Data1..Data8
  -> station_inputs
  -> status_mapper
  -> led_manager
  -> FastLED
  -> физическая LED-матрица
```

### 3.1. Аппаратные входы

`src/board_config.h` задаёт восемь GPIO, active-low логику и
`DEFAULT_ACTIVE_PORT_COUNT = 2`.

`src/station_inputs.cpp`:

- читает Data1..Data8;
- преобразует LOW в активное состояние;
- публикует цельный `StationInputState` через короткую critical section.

Обычное чтение выполняет `Input_Task` каждые 50 мс. Если задача не создалась,
`loop()` выполняет резервное чтение с тем же целевым периодом. Резервный режим
зависит от длительности HTTP и других операций основного цикла, поэтому это
аварийная деградация, а не равноправный штатный режим.

### 3.2. Статусы портов

`src/status_mapper.cpp` связывает:

- Data1/Data2 с Port1;
- Data3/Data4 с Port2;
- Data5/Data6 с Port3;
- Data7/Data8 с Port4.

Для активного порта приоритет фиксирован:

```text
error > charging > waiting
```

При текущем `DEFAULT_ACTIVE_PORT_COUNT = 2` Port1 и Port2 активны, Port3 и Port4
зарезервированы. Status mapper публикует защищённый snapshot, который читают LED
runtime и `/diagnostics`.

### 3.3. Светодиодный runtime

`src/led_manager.cpp` хранит текущую конфигурацию матрицы, карту зон, настройки
свободных зон и заранее разобранные кэши слоёв.

Штатно `LED_Task`:

- работает на core 1 с priority 1;
- обновляет временные эффекты и кадр примерно раз в 25 мс;
- получает `ledMutex` максимум на 10 мс;
- отправляет итоговый кадр через `FastLED.show()`.

Текущий reliability pass:

- проверяет создание `ledMutex`;
- проверяет запуск `LED_Task`;
- не запускает задачу с `NULL` mutex;
- включает неблокирующий `led_loop()` как fallback, если задача не создана;
- использует общий `led_update_step()` для задачи и fallback;
- показывает `mutexReady`, `taskStarted` и `loopFallback` в `/diagnostics`;
- удаляет лишний повторный refresh после сохранения free zone.

Нормальная задача и loop fallback не работают одновременно:
`led_loop()` немедленно выходит, если `LED_Task` успешно запущена.

### 3.4. Матрица и зоны

Текущая модель намеренно фиксированная:

- размер матрицы задаётся при сборке;
- количество активных портов задаётся при сборке;
- zone ID фиксированы;
- `zoneMap` хранится по физическим LED index;
- status layers и free custom layers хранят координаты `x-y`;
- topology преобразует координаты в физический индекс;
- при смене topology backend пересчитывает только `zoneMap`, сохраняя визуальные
  координаты зон;
- status/free layers не пересчитываются, потому что уже координатные.

При несовпадении сохранённого размера с compile-time размером matrix config
сбрасывается к defaults, а несовместимые status/free layers очищаются. Миграции
между размерами нет, что для текущей фиксированной модели безопаснее remap с
неясным смыслом.

### 3.5. Хранение

Используются три NVS namespace:

| Namespace | Назначение |
|---|---|
| `led_settings` | matrix config, zoneMap, status layers, free-zone configs и custom layers |
| `net_cfg` | STA, DHCP/static IP и AP fallback |
| `auth_cfg` | имя и пароль Basic Auth |

`matrix_cfg` хранится бинарной версионированной структурой. Слои хранятся как
ограниченные JSON-строки, но разбираются в фиксированные массивы только при
загрузке/сохранении, а не каждый LED-кадр.

Записи актуальных matrix/status/free/network/auth данных проверяются read-back.
Многошаговые операции имеют best-effort rollback, но NVS не является
транзакционной базой: потеря питания между двумя ключами всё ещё может оставить
согласованность на ответственности startup validation/default recovery.

### 3.6. Служебные части

`src/network_config.cpp` реализует неблокирующий STA-first, watchdog, reconnect,
controlled AP fallback и асинхронный Wi-Fi scan. Постоянный AP+STA не используется;
AP+STA включается временно только для scan из AP fallback.

`src/auth_config.cpp` защищает UI, API и OTA через Basic Auth. Стандартные
credentials `admin/admin` и AP password `12345678` допустимы только до ввода
конкретного устройства в эксплуатацию.

`src/main.cpp` регистрирует HTTP handlers, формирует/проверяет JSON, связывает
storage с LED runtime и обслуживает локальную web OTA. OTA принимает `.bin` и
проверяет результат ESP32 Update API, но пока не подтверждает принадлежность
образа именно этому продукту.

## 4. Оценка архитектуры

### 4.1. Провальных решений не найдено

В текущем масштабе проекта приемлемы:

- один `main.cpp` с HTTP handlers;
- один `gui_html.h` в PROGMEM;
- ручной ограниченный JSON parsing;
- JSON-строки небольших слоёв в NVS;
- бинарный `matrix_cfg`;
- фиксированная модель зон;
- compile-time matrix size и activePortCount;
- отдельные Input и LED tasks;
- отдельные network/auth modules.

Это не идеальная универсальная платформа, но это подходящая архитектура
standalone LED-контроллера. Большой rewrite сейчас создаст больше риска, чем
устранит.

### 4.2. Что работает, но ограничивает развитие

1. `cfg`, `zoneMap` и `freeZoneConfigs` публично доступны из `led_manager.h`.
   HTTP handlers меняют часть этих данных напрямую, пока LED task может их
   читать. Для текущего размера наиболее вероятное следствие — один
   несогласованный кадр, но формально это конкурентный доступ.
2. `MatrixConfig` и `FreeZoneConfig` объявлены в `led_manager.h`, поэтому storage
   зависит от модуля вывода. Это долг сопровождения, но не самостоятельный
   production blocker.
3. Ручной JSON parsing приемлем для текущих простых payload, но будет неудобен
   при появлении сложных вложенных API. Сейчас переход на ArduinoJson не окупает
   риск.
4. `gui_html.h` занимает около 125 КБ исходного текста и остаётся удобным до тех
   пор, пока UI меняется редко. Его размер не означает такой же постоянный расход
   RAM, потому что страница хранится в flash/PROGMEM.
5. JSON-слои хорошо подходят для матрицы 12x8, но не являются моделью для очень
   больших матриц или десятков слоёв.

### 4.3. Что спроектировали бы иначе с нуля

Новый проект с теми же требованиями стоило бы сразу начать с:

- закрытого состояния LED runtime и методов `get snapshot`/`apply`;
- отдельного файла с типами матрицы, не принадлежащего renderer;
- маленького модуля системной диагностики;
- firmware identity/version с первого OTA;
- исходных HTML/CSS/JS с генерацией одного PROGMEM header на этапе сборки.

Остальные ключевые решения — прямые Data-входы, mapper, фиксированные зоны,
compile-time hardware config, отдельные input/LED tasks, NVS и локальная web OTA —
можно было бы оставить такими же.

## 7. Что не переносить без отдельного требования

- EVSE business logic;
- OCPP, MQTT, RAPI, POS, Tesla и Emoncms;
- ArduinoOTA и OCPP remote OTA;
- update-by-URL без утверждённой серверной архитектуры;
- старый frontend и его сборочную/файловую структуру;
- LittleFS/SPIFFS только ради одного UI;
- физический live preview без отдельной error-safe сессии и timeout;
- runtime matrix size;
- динамические произвольные зоны;
- multi-matrix outputs;
- brightness schedule;
- HTTPS, cloud и signed OTA до отдельной модели угроз и требований.

Эти функции не являются признаком готовности standalone LED-контроллера.
Некоторые из них заметно увеличат Flash/RAM, поверхность отказа и стоимость
поддержки.

## 8. Подтверждённые технические долги

### 8.1. Публичное изменяемое LED state

**Факт:** `cfg`, `zoneMap` и `freeZoneConfigs` объявлены `extern`, а некоторые
handlers в `main.cpp` присваивают их напрямую.

**Риск:** LED task может увидеть частично обновлённую структуру. Вероятность
небольшая, последствие обычно ограничено одним кадром, но затрагивает основной
индикатор.

**Минимальное решение:** скрыть изменяемое состояние в `led_manager.cpp`;
предоставить snapshot и атомарные apply-методы под `ledMutex`. Не менять
renderer, API и NVS.

**Приоритет:** до пилота.

### 8.2. Системная диагностика

Stage 3 разделён на независимые части. Stage 3A реализован и успешно собран
командой `pio run -e esp32dev`; теперь он ожидает ручную проверку на ESP32. Он
добавляет:

- firmware version, build identity и environment;
- 64-битный uptime;
- текущий и минимальный free heap;
- стабильную строковую причину reset;
- `Input_Task` started/fallback и возраст последнего полного обновления входов;
- возраст последнего LED-кадра вместе с существующими LED runtime flags;
- результат последней попытки запуска AP fallback.

Результат сборки Stage 3A: RAM 49 672 байта (15,2%); Flash 1 002 237 байт
(76,5%).

Перед подготовкой каждой официальной прошивки разработчик обязан обновить
`FIRMWARE_VERSION` и `FIRMWARE_BUILD_ID` в `src/firmware_version.h`.

Расширенная диагностика NVS сознательно вынесена в будущий Stage 3B. Пока не
различаются отсутствующий, несовместимый и недоступный storage, не публикуется
`usingRamDefaults` и не ведётся журнал ошибок во Flash.

**Приоритет:** вручную проверить успешно собранный Stage 3A на ESP32; Stage 3B
требуется отдельно до unattended production и оценивается перед пилотом по
результатам испытаний.

### 8.3. Стандартные credentials

**Факт:** web использует `admin/admin`, AP — `12345678`, пока инженер их не
изменит. Basic Auth и AP password хранятся в NVS открытым текстом.

**Риск:** известные пароли дают доступ любому участнику той же сети или AP.
Basic Auth без HTTPS не защищает credentials от перехвата в недоверенной сети.
Пароли не возвращаются в HTTP-ответах, но при сохранении и при Basic Auth
передаются по обычному HTTP без шифрования. Это принятое ограничение локальной
инженерной сети, а не новый дефект Stage 4.

**Минимальное решение Stage 4:** стандартные пароли разрешены только для
первичной настройки. `/auth_status` сообщает булевый `defaultCredentials`, а
`/network_status` — булевый `defaultApPassword`. Разделы «Безопасность» и «Сеть»
показывают отдельные предупреждения, пока соответствующие стандартные данные
используются. Предупреждения не блокируют UI, OTA, настройку или runtime.

Перед установкой контроллера инженер обязан изменить оба пароля и выполнить
commissioning checklist из `README.md`. Устройство нельзя считать введённым в
эксплуатацию, пока оба стандартных пароля не заменены.

Принудительный first-login flow, hashing и HTTPS не обязательны для стенда и
пилота в изолированной инженерной сети, если процедура выполняется и
проверяется. Physical reset, reset auth, HTTPS и hashing остаются сознательно
отложенными.

**Приоритет:** процедура до пилота; более сильная техническая политика — по
результатам пилота и модели угроз.

### 8.4. Static IP policy

**Факт:** static IP поддерживается, но неправильные IP/gateway/mask/DNS способны
сделать STA недоступной.

**Минимальная политика пилота:** DHCP плюс reservation на роутере объекта,
известный IP в паспорте устройства. Static IP в UI не использовать без данных
сетевого инженера.

Полный MAC STA-интерфейса теперь возвращается строкой `staMac` через защищённый
`/network_status` и показывается в разделе «Сеть». DHCP reservation создаётся
на роутере по этому полному STA MAC, а не внутри ESP32. Уникальный DHCP hostname
имеет вид `led-controller-xxxxxx`; его suffix совпадает без учёта регистра с
suffix автоматически созданного default AP SSID. Hostname не заменяет MAC и не
гарантирует доступ к web UI по имени. mDNS не добавлялся.

**Минимальное будущее исправление:** проверять очевидно невозможные комбинации и
показывать предупреждение до сохранения. Полный автоматический rollback не нужен,
пока DHCP reservation является штатным сценарием.

**Приоритет:** процедура до пилота; код после пилота, если static IP реально
используется.

### 8.5. OTA product identity

**Факт:** backend проверяет наличие файла, расширение `.bin`, запись и завершение
ESP32 Update API. Он не проверяет, что образ собран именно для Test-led.

**Риск:** инженер может загрузить технически валидный, но чужой ESP32 image.

**Минимальное решение:** добавить version/product marker и проверку identity до
начала регулярных удалённых OTA.

Проверка принадлежности образа не является блокером для стенда. Она также не
обязательна для контролируемого пилота, если OTA выполняет ответственный инженер
проверенным `firmware.bin` с зафиксированной версией или hash. Product identity
становится обязательной перед регулярным удалённым OTA через VPN или unattended
production.

Signed OTA и rollback остаются отложенными до отдельной модели угроз или
массового удалённого обновления.

**Приоритет:** перед регулярной remote OTA и unattended production.

### 8.6. Ошибки NVS, AP и задач

Подтверждено:

- часть load-path вызывает `Preferences.begin()` без проверки результата;
- результат `WiFi.softAP()` теперь сохраняется для диагностики как
  `not_attempted`, `ok` или `failed`, без изменения recovery-архитектуры;
- Input task/fallback и возраст последнего обновления теперь доступны в
  diagnostics;
- LED task/mutex/fallback и возраст последнего кадра доступны в diagnostics;
- save-path в основном проверяет запись и read-back.

Оставшаяся работа Stage 3B: не смешивая storage-модули, различить ошибку NVS
load и нормальное отсутствие настроек. Она не входит в текущий Stage 3A.

**Приоритет:** до пилота для diagnostics/critical startup flags; подробный журнал
не обязателен.

### 8.7. Смена activePortCount

`activePortCount` задаётся при сборке через `DEFAULT_ACTIVE_PORT_COUNT`. Если
после эксплуатации изменить значение, например с 2 на 3, старая сохранённая
`zoneMap` автоматически не перераспределяется.

Port3 начнёт вычислять статус по Data5/Data6, но физически не будет виден, пока
для него не назначены пиксели. UI предупреждает, что активная зона Port3 не
размечена, а сохранение новой невалидной карты блокируется.

Автоматически сбрасывать пользовательскую разметку не нужно. Изменение
`activePortCount` является процедурой смены аппаратного варианта: после новой
сборки и прошивки инженер обязан вручную проверить и при необходимости
переразметить все активные порты.

Это ограничение не требует обязательного рефакторинга storage.

### 8.8. Скрытые пиксели custom layer

После изменения `zoneMap` старые координаты пользовательского рисунка свободной
зоны могут остаться в NVS. Пока координата принадлежит другой зоне, LED runtime
игнорирует этот пиксель custom layer, поэтому он не может перекрыть статус порта
или error.

Если позднее вернуть координату той же свободной зоне, старый рисунок может
появиться снова. Автоматическую очистку пока не выполняем, чтобы неожиданно не
удалять пользовательский рисунок. После изменения границ свободной зоны инженер
должен проверить её custom layer и при необходимости очистить рисунок вручную.

**Приоритет:** низкий; эксплуатационное ограничение, не blocker.

## 9. Классификация мер

### 9.1. Обязательное изменение кода

- зафиксировать и сохранить LED reliability pass;

- сменить web и AP credentials;
- использовать DHCP reservation;
- записать IP, AP SSID и идентификатор устройства;
- использовать только проверенный firmware.bin;
- сохранить версию установленной прошивки;
- выполнить acceptance checklist и приложить результат;
- не включать static IP без согласованных параметров сети.
- после изменения `activePortCount` вручную проверить и переразметить все
  активные порты;

- captive portal;
- малый журнал последних ошибок;
- stronger credential storage;
- static-IP rollback;

## 11. Hardware acceptance checklist

### Входы и статусы

- [ ] Data1 LOW распознаётся как charging Port1.
- [ ] Data2 LOW распознаётся как error Port1.
- [ ] Data3 LOW распознаётся как charging Port2.
- [ ] Data4 LOW распознаётся как error Port2.
- [ ] HIGH на каждом входе означает неактивный сигнал.
- [ ] Data1 LOW + Data2 HIGH даёт charging.
- [ ] Data1 HIGH + Data2 LOW даёт error.
- [ ] Data1 LOW + Data2 LOW даёт error.
- [ ] Data1 HIGH + Data2 HIGH даёт waiting.
- [ ] Те же четыре комбинации проверены для Data3/Data4.
- [ ] Одновременные состояния Port1 и Port2 отображаются независимо.
- [ ] Измерена задержка Data error -> физическая error-индикация.
- [ ] Во время Wi-Fi scan/reconnect/HTTP/OTA Data snapshots продолжают меняться.
- [ ] На реальном сигнале оценены дребезг и помехи; debounce добавляется только
      при подтверждённой необходимости.

### Матрица

- [ ] Startup animation показывает красный, синий, зелёный по одному разу.
- [ ] Активный error до старта пропускает/прерывает startup animation.
- [ ] Фактический порядок цветовых каналов соответствует `BRG`.
- [ ] Проверены все четыре topology на тестовом рисунке.
- [ ] После смены topology зоны остаются в тех же логических координатах.
- [ ] Status layers и free custom layers после смены topology не смещаются.
- [ ] Port1/Port2 waiting, charging и error соответствуют UI.
- [ ] Free zones static/custom/rainbow работают одновременно с port zones.
- [ ] Free zone не скрывает port error, потому что один пиксель принадлежит
      только одной zone.
- [ ] Неразмеченный активный порт виден в UI warning и не сохраняется как
      валидная новая zoneMap.
- [ ] Измерены максимальный ток и нагрев при ярком белом/типичном кадре.
- [ ] Бюджет FastLED 12 В / 3000 мА соответствует реальному питанию и матрице.

### Сеть и UI

- [ ] Первый старт без SSID поднимает уникальный AP fallback.

- [ ] Wi-Fi scan возвращает 202 во время работы и затем список сетей.
- [ ] Scan из AP fallback временно использует AP+STA и возвращается в AP-only.
- [ ] UI восстанавливается после временной потери связи и не переходит навсегда
      в локальный mock mode.
- [ ] DHCP/static настройки дают ожидаемый IP; для пилота используется DHCP.

### Storage, reboot и OTA

- [ ] Zones сохраняются, восстанавливаются после reload и reboot.
- [ ] Каждый status layer сохраняется и восстанавливается.
- [ ] Free mode/color/brightness/custom layer сохраняются и восстанавливаются.
- [ ] Port brightness и free-zone brightness сохраняются без записи чужих полей.
- [ ] Topology и remapped zoneMap восстанавливаются после reboot.

- [ ] Пустая NVS создаёт ожидаемые defaults.
- [ ] Невалидная matrix config безопасно сбрасывается.
- [ ] Отключение питания во время сохранения не оставляет опасную индикацию;

- [ ] Корректный firmware.bin успешно обновляет устройство и перезагружает его.

- [ ] В обычном режиме diagnostics показывает `LED taskStarted=true`.

**Статус:** реализация завершена, ожидает локальной сборки и ручной проверки на
ESP32 и в DHCP-клиентах роутера.

**Результат:** `/network_status.staMac` всегда является строкой полного STA MAC;
раздел «Сеть» показывает это значение. Hostname изменён с одинакового
`led-controller` на стабильный `led-controller-xxxxxx`. Шесть строчных
hex-символов берутся из тех же младших 24 бит eFuse/chip ID, что и uppercase
suffix default AP SSID. DHCP reservation остаётся настройкой роутера.

**Границы:** network state machine, DHCP/static-IP policy, AP fallback, AP SSID,
NVS, auth, OTA и пароли не изменялись. Hostname не публикуется через mDNS и не
гарантирует доступ по имени.

**Build ID:** `network-identity-20260729`.

### Stage 5 — OTA product identity

**Цель:** уменьшить риск загрузки чужого ESP32 image и обеспечить видимую
версию.

**Вероятные файлы:** `src/main.cpp`, новый небольшой header с product/version
metadata, `src/gui_html.h`, build flags в `platformio.ini` при необходимости.

**Риск:** средний: неверная проверка может заблокировать штатную OTA. Нужен
локальный USB recovery test.

**Flash/RAM:** небольшие константы и parsing header/manifest; без постоянного
буфера полного firmware image.

**Тесты:** корректный образ, чужой образ, повреждённый/оборванный upload,
повторная OTA, reboot, локальное восстановление.

**Критерий завершения:** UI показывает установленную version/build; backend
отвергает образ с неверной product identity до активации обновления.

**Не смешивать:** cloud update, signed OTA, partition redesign и OCPP/MQTT.

### Stage 6 — полная regression и pilot soak

**Цель:** подтвердить совместную работу всех изменений на реальном устройстве.

**Вероятные файлы:** код не меняется, кроме отдельных исправлений найденных
дефектов; протокол release/acceptance обновляется отдельно.

**Риск:** низкий для начала этапа; найденные дефекты оцениваются отдельно.

**Flash/RAM:** без планового влияния; фиксируются фактические build metrics и
минимальный free heap.

**Тесты:** полный hardware и pilot checklist, многосуточный soak, power/router
cycling, repeated saves, OTA, normal/fallback paths.

**Критерий завершения:** нет потери error-индикации, утечки доступной памяти,
непредсказуемого reset или потери доступа; release artifact и процедура
восстановления утверждены.

**Не смешивать:** новые продуктовые функции. Любая найденная проблема
исправляется отдельным commit и запускает относящуюся к ней regression заново.

## 15. Ресурсы ESP32

Текущая оценка:

- `gui_html.h` — около 125 КБ исходного текста в PROGMEM;
- matrix 12x8 даёт небольшие фиксированные arrays и layer caches;
- Input task stack 2048, LED task stack 4096;
- регулярный LED-кадр не создаёт динамические `String`;
- большие `String`/JSON создаются по HTTP-запросу или при загрузке слоя, а не
  каждый кадр;
- diagnostics polling активен часто только при открытой вкладке;
- единственная внешняя библиотека проекта — FastLED.

Подтверждённой критической проблемы Flash/RAM нет. Точные значения занятой flash,
static RAM, минимального free heap и task high-water marks должны быть измерены
на Stage 1/3. Старый `.pio` artifact нельзя использовать как точную метрику
текущего незакоммиченного дерева.

## 17. Решения по спорным пунктам

### Нужна ли ArduinoJson сейчас

Нет. Текущий API небольшой, payload ограничены, координаты и цвета проходят
специализированную validation. Переход не удалит business rules и создаст
широкий regression. Возвращаться к вопросу нужно только при заметном росте
вложенности API. Flash/RAM сравниваются двумя реальными сборками, а не оценкой
«на глаз».

### Нужно ли разделять `main.cpp`

Не сейчас. После Stage 3/5 можно вынести diagnostics или OTA, если файл продолжит
расти и тестирование handlers станет неудобным. Делить только ради длины файла
не нужно.

### Нужно ли разделять `gui_html.h`

Не для production readiness. При необходимости сопровождения следует хранить
исходные HTML/CSS/JS отдельно и генерировать один PROGMEM header. LittleFS ради
этого не нужен.

### Нужно ли менять NVS format

Нет. Текущий бинарный versioned matrix config и ограниченные JSON layers
соответствуют матрице 12x8. Новый формат оправдан при runtime size, большом числе
слоёв или необходимости настоящей транзакционной миграции.

### Нужны ли runtime matrix size и универсальная port model

Нет. Compile-time hardware parameters уменьшают ошибочные конфигурации. Текущая
модель уже поддерживает 1-4 порта через пары Data inputs и activePortCount.
Универсализация нужна только при новом аппаратном контракте.

## 18. Итоговое решение

**Стендовую плату сейчас прошивать можно.** Текущий код собран пользователем,
архитектурных blocker для контролируемого стенда не найдено.

**Ставить устройство в пилот сейчас рано.** Сначала нужно выполнить аппаратную
приёмку, зафиксировать reliability pass, закрыть публичное изменяемое LED state,
добавить системную диагностику и выполнить commissioning procedure.

**До unattended production не хватает:** подтверждённого hardware acceptance,
длительного soak, уникальных credentials, полной task/network/storage
диагностики, OTA product identity и проверенной процедуры восстановления.

**Следующий один рекомендуемый этап:** вручную проверить текущий успешно
собранный Stage 3A на ESP32. Stage 2, Stage 3B и hardware acceptance остаются
отдельными последующими решениями и не должны попадать в этот diff.

  readiness review, сравнение с `proj1`, архитектурная ретроспектива и текущая
